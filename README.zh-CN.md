# Agent Relay · 智能体接力

**让 Codex 团队并行开工、接力交付，把额度变成成果。**

[English](README.md) · [技能正文](skills/parallel-dev-coordination/SKILL.md) · [MIT 许可](LICENSE)

Agent Relay 让多智能体分工开发、持续接力、集中整合，减少等待与返工。特别适合在 Tibo（Codex 产品负责人）重置额度前集中冲刺，把剩余额度用在可验收的交付上。

Agent Relay 是一个用于 **Codex 并行软件开发协调**的技能。它把任务拆分、文件归属、交付接收、合批测试和下一批接续整理为可复用流程，减少空等、冲突和反复确认。

它适用于同一任务中的子智能体，也适用于用户已授权共同开发的独立对话。技能调用名称是 **`parallel-dev-coordination`**。

## 开发背景：为什么采用多对话协作

Agent Relay 起源于实际开发中的一个限制：**在开发时使用的 Codex 环境里，每个对话最多同时运行 3 个子智能体，主智能体不计入这 3 个名额。** 当项目有更多可以独立推进的模块时，只靠一个对话组织开发，就会受到这组子智能体名额的限制。

因此，我们采用了**多对话协作，让多个对话分别驱动各自的子智能体工作**：主协调对话负责项目分工、共享接口、成果接收和最终整合；其他开发对话负责独立模块，并在各自实际可用的名额内安排实现与审查。这样可以组织比单个对话更多的子智能体参与同一项目。

更多执行者也带来了新的协调问题：文件修改冲突、交付后无人接收、下一批没有真正派发，以及对临时中转对话的依赖。Agent Relay 将处理这些问题的实践整理为技能，让多对话及其子智能体按明确边界持续接力。

这里的“3 个”描述开发时所用环境，不代表所有 Codex 版本的固定上限。当前[官方配置文档](https://learn.chatgpt.com/docs/config-file/config-reference)列有单会话子智能体并发设置；实际可用数量以客户端、配置和运行时工具为准。多对话使用各自获准的执行能力，仍受账号额度及适用限制约束。

## 它解决什么问题

- **整合前先派工**：主线程开始整合上一批之前，先把就绪的独立任务交给可用执行者。
- **一个文件一个修改者**：提前划清专属文件和共享接口，减少覆盖与返工。
- **交付有人接收**：完整交付后及时给出接收或具体返修结论，同时准备下一批。
- **空闲及时发现**：临时复用闲置子智能体做事件观察；开发需要现有名额时，由主线程直接观察，不频繁轮询。
- **正式派工一次落地**：记录并发送绑定冻结规格的派工回执，旧“预留”文字不再盖过有效开工决定。
- **按批次选择运行设置**：获用户授权后，按工作难度选择模型与推理强度，通过工具应用并核对实际生效值。
- **昂贵测试合批做**：独立检查并行，实际共享资源统一协调。
- **复测只选失败项与受影响项**：复用相关输入未变的通过证据，纳入新增功能和共享修改的实际调用者，避免每次小修重跑无关整组流程。
- **减少重复上传**：先用有界运行结果定位；图片字节、相关输入和当前状态证据一致时才复用原视觉结论，保留首次及受影响图审。详见[上传与视觉证据规则](skills/parallel-dev-coordination/references/upload-efficiency.md)。这些是工作流程规则，Agent Relay 尚不自动拦截图像上传、恢复 WebSocket 或清除历史请求体。
- **桌面输入不争抢**：隐藏窗口、不同端口和不同工作树，都不自动隔离系统鼠标与键盘。
- **进度有证据**：开发、模块接收、整合、图审、实机和线上验收分别记录。

目标是增加已接收成果、减少等待和返工；不是单纯让更多智能体显示为“运行中”。

## 开始使用

在已有项目中输入：

```text
使用 $parallel-dev-coordination 组织这个项目的剩余开发。
使用当前任务实际可用的子智能体，先分配独立模块再开始整合。
每个文件只安排一个修改者，保持原功能范围和验收标准，
复用现有测试入口与有效证据。
```

这段指令不会要求创建另一个独立对话。需要多个对话共同开发时，明确身份与通信授权：

```text
使用 $parallel-dev-coordination。
主协调对话是：[线程 ID、主机]。
并行开发对话是：[线程 ID、主机]。
我授权双方就本项目直接互发分工、接口问题、交付、接收及返修消息。
开发范围限定为：[具体范围]。复用已有对话。
```

将授权提供给参与的各个对话，或使用宿主支持的可信授权机制。收到另一智能体的消息，本身不构成回复授权。

长期协作需用真实分工和交接消息验证主线程与每个执行者的双向直达。只列出旧执行者的约定不自动覆盖新增对话；临时旁支不应成为唯一中转，旁支结束后，写好的派工文件不会自行通知执行者。详见[长期协作的通信路径](skills/parallel-dev-coordination/references/contracts-and-goals.md#长期协作的通信路径)。

需要新建独立对话时，应由用户明确提出；技能不会为增加并发名额不断新建对话。

## 工作方式

```mermaid
flowchart LR
    A[就绪的独立批次] --> B[明确负责人、文件和接口]
    B --> C[实现与必要验证]
    C --> D[交付代码和证据]
    D --> E{主线程审查}
    E -->|具体返修| C
    E -->|模块接收| F[整合与剩余验收]
    D -. 准备下一批 .-> A
```

主线程整合上一批时，其他执行者可以开发下一批。必须区分“预留下一批”和“允许立即开工”：仍有依赖或尚未授权的任务，不能因为已经写入计划就直接开始。

已按哈希引用的规格与当前执行状态分开保存。有权派工者在现有任务账本登记负责人、规格版本、开工决定及前置条件，再把同一回执发给执行者。原规格保持不变，旧预留状态由正式回执明确承接；有效回执已经允许开工时，不因原规格还写着“预留”再次请求许可。更新的用户暂停、文件归属冲突和未满足依赖仍须遵守。

登记完成、消息送达和实际开工分别核实。通知失败时先核对原回执与执行者状态，再补送同一分工。复用已有账本和消息工具，Agent Relay 不安装派工服务。

恢复上下文后，如果旧检查点写着“串行”或“无权派工”，而用户已更新 Goal，执行者应先独立读取自己的当前 Goal，再纠正过时记录。检查点较新的保存时间不代表旧指令重新生效；钩子注入也不会自动赋予记录新的权限。修复接力必须核对真实批次的 Goal 读回和有效实现差异，不能只更新技能或发送通知就宣布成功。

| 角色 | 主要责任 |
| --- | --- |
| 主协调者 | 范围、依赖、共享接口、整合、接收和最终验收 |
| 模块执行者 | 归属文件、内部委派、模块检查、交付和相关返修 |
| 审查者 | 对照需求与证据进行有边界的审查，不自动取得其他文件修改权 |

如果待整合成果积压，先消化整合和返修，再增加派工。不为填满名额制造工作。

## 观察空闲并接续下一批

并行工作已获授权时，主线程可临时复用已有闲置子智能体，给它明确观察目标和有限观察区间。现有子智能体有就绪开发任务时优先开发，由主线程直接观察。Agent Relay 不常驻占用监控名额，也不安装后台服务。

使用宿主的事件等待接口，如 `wait_threads`，为每个目标保留游标、所见轮次／批次和已处理决定。状态未变时不重读整段历史、不发重复消息。某个已空闲目标反复立即返回同一旧事件时，先将它移出当前等待集合，等新派工或正常交接检查再纳入。

观察者区分开发中、待接收、需返修、等待依赖及已接收但无下一批；向自己的主线程报告可行动的变化、候选下一批、依赖和文件冲突。它不向独立执行者发消息、不正式派工，不改对方 Goal、标题、模型或共享项目文件。

主线程在较长整合／测试前及收到交付后处理观察结果：接收或提出返修，正式派发已就绪的独立任务，或记录阻止开工的具体依赖。每个执行者最多预留一个下一批。观察区间结束或开发需要该子智能体时，将观察责任交回主线程。

记录实际观察方式、游标、首次真实检查、主线程决定、派工送达和有效工作推进证据。安排启用、消息送达、前置核查和有效实现分别报告；active 标志或通知成功不能证明代码接力恢复。一次成功不等于长期不断档。

详见[观察者职责与接续核验](skills/parallel-dev-coordination/references/contracts-and-goals.md#观察者与首次接续核验)。

有界监督还提供[本地状态与接续入口](skills/parallel-dev-coordination/references/supervision.md)：共享恢复/通知额度、待命复查、确认后的决定及行动跟踪。主线程和参与对话承担实际执行；安装旁支不作为长期调度者。主线程忙于手机测试时，也在安全操作边界评估不冲突的已授权工作。

Python reducer不会自行调用聊天工具、安装定时监控或唤醒模型；获准宿主提供新鲜观测并消费一次性通知许可。真实原生控制接口、独立告警和实际派工分别验证，未接通的能力保持关闭，不把本地测试当作完整后台监督已上线。

重复核验嵌套 `path + sha256` 时，可复用[交付引用只读核验工具](skills/parallel-dev-coordination/references/delivery-verification.md)。审查进度和等待依赖补充在原接收记录中，并绑定冻结交付哈希；字节一致不能代替语义审查、视觉验收或实际开工证明。

## 模型与推理强度

每批正式派工前，评估不确定性、错误后果和依赖复杂度。用户授权按任务选择后，主线程可为明确的小任务选择较轻模型，为复杂状态或架构问题提高推理强度。同等难度可以沿用；用户固定设置与预算优先，不为切换模型中断在途工作。

在已有派工回执记录目标设置、理由、工具结果和实际运行证据。创建 Goal 或在消息里写模型名，不等于已经应用设置；独立对话与子智能体的工具和继承规则也可能不同。实际设置无法读回时标记待核验，继续不受影响的工作，不宣称切换成功。

具体选型起点与应用方式见[模型选择与生效核对](skills/parallel-dev-coordination/references/model-routing.md)。Agent Relay 提供执行规则，不是自动切换模型的服务。

## 示例：一个主线程和三个执行者

| 执行者 | 当前工作 | 修改边界 |
| --- | --- | --- |
| 主线程 | 整合已经交付的设置窗口 | 共享状态、导航及客户端接线 |
| 执行者 A | 开发通讯录窗口 | 通讯录专属界面和素材 |
| 执行者 B | 开发过场组件 | 过场专属着色器、界面和素材 |
| 执行者 C | 审查此前冻结的模块 | 只读审查及证据 |

每批明确输入输出和检查条件。需要共享状态变化时，由执行者提出具体接口需求，主线程维护共享文件。模块符合交付条件就及时接收，实机和完整流程验收继续单独记录。

这里的数量只是示例，不代表固定或保证的并发额度。

## 桌面与设备测试

两个隐藏的 GUI 测试窗口也可能相互干扰。例如 Godot 中的 `Input.warp_mouse()` 仍会操作共享指针。

技能要求复用项目的**统一输入互斥入口**：

- 只有实际影响系统输入或焦点的测试需要该资源锁。
- 获取锁必须是原子操作；先查“没有进程”再启动，仍存在竞争窗口。
- 一批入口持锁一次，区分外层包装和自身持锁的 runner，避免重复加锁。
- 异常或超时先停止本方输入进程，再释放控制权。
- 回收失效锁须核对拥有者和关联进程，不能只看时间。
- 无界面或进程内测试，在可写状态隔离、无系统输入副作用时可以并行。

**本仓库提供协调规则，不包含可执行的输入锁实现。** 优先复用项目已有机制。尚无机制时，按批次约定一次测试时段，再由明确负责人补充小范围共享入口，不必建立另一套调度平台。

详见[共享输入与测试隔离](skills/parallel-dev-coordination/references/shared-input.md)。

## Goal 和下一批接续

普通任务不必强制建立 Goal。用户明确授权按批次使用 Goal 时：

1. 将用户确认的完整固定协作规则与当前批次分开，明确范围和完成条件。
2. 实现、验证并交付。
3. 取得约定接收，保留未完成的整合或实机验收事项。
4. 满足本批完成条件后，才将当前 Goal 标为完成。
5. 下一批分工及创建授权明确时，核对完整候选正文符合宿主当前长度限制，再由对应对话创建“完整固定规则＋新批次”的 Goal，仅更新批次内容。
6. 创建后立即用独立读取工具核对完整正文、批次及状态；在上下文恢复和交接时再次核对。

用户要求对话名称随 Goal 更新时，执行者在新 Goal 核验后同步标题，保留项目／角色／编号前缀，只更新当前任务部分；主线程在交接时核对工具返回的名称。预留下一批不提前改名，名称更新、Goal 核验和模型设置生效分别检查。

发送候选 Goal 前和创建前检查长度，标题及固定规则也计入；不把某个客户端的上限视作通用常量。必要时只去掉当前批次描述的重复内容，保留范围、文件归属、接口及验收条件；用户要求逐字保留的文本不能自行精简。

不要用紧凑摘要或“沿用之前要求”代替已确认的固定规则。仍超过宿主限制时保留原文并说明限制；只有用户已接受引用式承载，才改用可读取、版本明确的规则文档，并在接续时实际核对。用户要求全文保留时不能自行改成引用。

**创建返回成功不等于独立读回已验证。** 读回为空或不一致时，先检查查询、对话身份、用户暂停／清除、预算及并发更新；原因不明时报告，不直接重建。只有确认仍有有效授权、无未完成目标且排除了上述情况，才最多补建一次并再次读回。不得覆盖已有目标或绕过用户控制及预算限制。

跨对话消息不会直接改写另一个对话的 Goal。技能不替换未完成目标，不为换任务虚报完成，也不创建后台自动唤醒服务。没有下一批分工时，等待消息，不自行创造任务。

技能提供操作规则，不负责存储 Goal，不能保证目标永不丢失。规则继承、创建响应、独立读回和 UI 显示应分别核实；未经定位不宣称异常由应用或技能导致。关于 Goal 的对话状态及生命周期，参见 [OpenAI 官方文档](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)。

可复用文案见[派工、交付与批次 Goal](skills/parallel-dev-coordination/references/contracts-and-goals.md)。

## 模型容量故障恢复

另提供可选的 [Goal 暂停与恢复保护](skills/parallel-dev-coordination/references/goal-lifecycle.md)：通过原生工具 hook，将一次暂停绑定到本轮新的人类指令，核对真实 Goal，阻止旧暂停重放。安装保留已有 hook，须经原生审核；它不会自行恢复目标、写 Codex 数据库或重置预算，文件安装完成不等于已生效。

仓库提供可选的[宿主恢复程序](skills/parallel-dev-coordination/references/capacity-recovery.md)：只识别明确容量故障，等原生重试结束后有限退避，保持 Goal、暂停状态、文件归属与推理强度。备用模型仅接受明确获准的 `gpt-6.1-sol`，固定模型的对话仍只重试原模型。发送结果不明时停止重发，失败前已执行的动作须先核对真实结果。

程序不依赖模型判断，默认只观察，运行时间有限。执行模式要求原宿主开放可连接的 app-server 控制 socket，并明确恢复授权和唯一派发所有者；只有专属 stdio 的桌面无法直接接入。已执行工具的失败还需要项目结果核对适配器。代码测试、宿主接入、请求接受和真实任务恢复分别验收；不自动安装服务、创建定时任务或接管现有开发聊天。

## 使用边界

这个技能不提供额外并发名额、更多账号额度或确定的加速倍数，也不自动授予新建对话、跨对话消息、发布代码或操作生产系统的权限。

它不会安装后台服务、插件服务器、通用调度器或鼠标控制程序，也不替代项目自身的需求和验收标准。可选容量恢复程序只有显式启动后才运行；实际能力取决于当前客户端、工具及权限。

技能正文目前为中文，README 提供中英文版本。不绑定任何游戏、引擎、项目路径或固定对话 ID。
