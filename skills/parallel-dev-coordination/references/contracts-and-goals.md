# 批次约定与 Goal

模板只帮助表达已授权事项，不会产生新的权限。将方括号字段替换为当前核实的实际值；项目名称、线程 ID、路径和测试标准不从历史示例继承。已有任务卡字段等价时不要再建一份。

## 派工消息

```text
批次：[批次 ID 与模块名称]
结果：[可验收的业务/界面行为]
优先级及依赖：[已就绪条件；尚待接口]
执行者：[已核实的线程或子智能体身份]
允许新增/修改：[精确文件或明确专属路径范围]
共享归属：[由协调者保留的文件与服务]
接口：[输入快照/参数、输出请求/信号、错误与取消语义]
验证：[本批必要检查；主线程负责的后续检查]
输出：[依照项目约定的实际位置]
调度：[立即执行 / 仅预留，满足什么条件再开始]
接收者：[主协调者身份；消息授权已核实]
```

派工是一个交付单元，不是无边界的“继续把项目做好”。资料、实现和审查可以分开，但不要让多个执行者分别重做整套来源调查。拆出下一批时把当前批的返修归属一并保留。

## 交付消息

```text
批次与版本：[批次 ID、提交或文件哈希清单]
已实现：[本批明确范围]
接口与接入：[最小接线说明及兼容前提]
证据：[测试/截图/日志位置；本次执行或复用的依据]
未通过及未验证：[失败、待实机/线上等，明确归属]
共享变更需求：[无 / 必需事项与建议修改者]
资源状态：[仍在运行的本方进程、占用和需要保留的数据]
请求：[确认接收或具体返修；准备下一批分工]
```

接收者明确回复“本批接收”或具体返修项，说明这次接收覆盖的范围。只有测试通过但未做约定审查时，不冒称接收；已审查满足范围时及时给结论，不为了等待一个措辞而额外循环验收。不得因交付清单更新就使所有未变证据失效。

## Goal 轮转约定

以下是给用户审阅的授权文案，不是技能自动给予的授权：

> 用户授权协调对话 [ID/主机] 与执行对话 [ID/主机] 就本项目批次任务直接互发分工、接口、交付和接收消息。执行对话仅在当前 Goal 实际完成且下一批已明确分配后，按用户授权为下一批创建 Goal；保留范围、验收与输入隔离约束。

当前工具支持时，典型顺序为：核对现有 Goal → 当前批达到完成条件 → 标记完成 → 对明确分配且获授权的下一批调用创建工具。检查工具返回状态，不把发出指令当成已设置。

若当前工具只能修改状态，不能修改正文，不要求执行者“自行改写未完成 Goal”。可在原目标范围内更新批次计划；超出原范围或必须替换目标时，说明需要用户编辑或使用已授权、正式支持的接口。不直接改 Codex 数据库或会话文件，不伪造消息。也不要把普通跨对话消息当成用户的 Goal 编辑操作。

创建下一批时，可用以下紧凑骨架，加上该批真实分工：

```text
完成 [批次 ID/模块]，交付 [具体行为及产物]。
协调者为 [ID/主机]；文件归属与输入输出契约见 [当前任务记录]。
完成条件为 [实现、必要验证、交付资料和接收条件]。
沿用项目既有功能/视觉标准、共享资源隔离、发布及数据保护规则。
使用 parallel-dev-coordination 的当前适用流程；不扩大范围。
已核实的跨对话消息及下一批 Goal 授权为 [实际授权及边界]。
```

只有本批 Goal 完成，不等于整个项目完成。尚未分配的任务不是虚构的“下一批”。无下一批时结束本批并等待；如果用户要求未来主动跟进，另按环境支持的调度工具处理，不以技能文案冒充后台服务。

## 审查调度是否有效

有现成记录时比较：交付到接收的等待、待整合批次数、返修次数、共享资源等待，以及主线程是否仍在推进关键路径。不要为这些指标先造监控平台。

- 空闲发生在主线程整合期间：先检查能否准备独立下一批，而非立即增加名额。
- 多个批次都待接收：优先整合，限制新派工。
- 文件冲突持续发生：缩小修改范围或把共享接口收回单一负责人。
- 无新证据却频繁发消息：改为一次交付加有变化才通知。
- 主线程暂不可用：保存交付，不越权自我接收或伪造反馈。
