# 批次约定与 Goal

模板只帮助表达已授权事项，不会产生新的权限。将方括号字段替换为当前核实的实际值；项目名称、线程 ID、路径和测试标准不从历史示例继承。已有任务卡字段等价时不要再建一份。

## 派工消息

```text
批次：[批次 ID 与模块名称]
结果：[可验收的业务/界面行为]
优先级及依赖：[已就绪条件；尚待接口]
执行者：[已核实的线程或子智能体身份]
允许新增/修改：[精确文件或明确专属路径范围]
共享归属：[由协调者保留的文件与服务]
接口：[输入快照/参数、输出请求/信号、错误与取消语义]
验证：[本批必要检查；主线程负责的后续检查]
输出：[依照项目约定的实际位置]
调度：[立即执行 / 仅预留，满足什么条件再开始]
接收者：[主协调者身份；消息授权已核实]
```

派工是一个交付单元，不是无边界的“继续把项目做好”。资料、实现和审查可以分开，但不要让多个执行者分别重做整套来源调查。拆出下一批时把当前批的返修归属一并保留。

### 冻结规格与正式派发

任务规格描述做什么，派工回执描述当前由谁做、能否开始。已有规格被 Goal、测试或交付按哈希引用时，保持其字节不变；在现有任务账本中增加执行记录即可。规格编制时的“预留／未派发”保留历史含义，不作为永久开工限制。

主协调者或用户明确授权的派工者完成下面这组动作，不把它们声称为跨工具的原子事务：

1. 核对用户最新指令、负责人、真实依赖和文件归属。依赖上一批接收时，先记录实际接收及遗留返修责任。
2. 写入正式派工回执，绑定批次、规格版本／哈希、执行者、派工者、时间或修订号、立即执行或等待条件，以及取代的旧预留记录。沿用已有账本，不要求某种文件格式或新建服务。
3. 向该执行者发送一次同内容通知，给出回执的可读位置或完整正文。需要唤起空闲的已授权对话时，使用宿主支持的发送消息工具；仅写文件不等于已通知。
4. 按实际结果分别记录登记、发送和开工。发送失败或中途恢复时先检查原回执及执行状态，再补送同一分工，不重复分配或启动另一位作者。

可直接加进现有派工记录的字段：

```text
派工者／执行者：[已核实身份及授权]
批次／规格：[批次 ID、可读位置、冻结版本或哈希]
回执版本：[时间或修订号；已有账本定位]
当前决定：[立即执行 / 等待明确条件]
前置条件：[已满足的接收依据，或尚待事项]
取代记录：[同批次、同规格、同负责人的旧预留状态]
保留事项：[上一批返修及后续整体验收归属]
```

执行者收到有效回执后核对身份、规格和条件，满足则执行；需要 Goal 时按下文创建并独立读回。不能因为冻结规格还写着“预留”而再等旁支转达或用户重复确认。较新的用户暂停／撤销、预算限制、冲突的负责人或规格变更仍须处理；“消息较新”本身不能赋予权限或覆盖这些约束。

若只有第三方建议、回执缺失或范围确实矛盾，向有权派工者一次说明具体缺项，保留不受影响的已授权工作。不要在多个对话间循环求证同一事实，也不由执行者伪造主线程的接收或派工决定。

## 交付消息

```text
批次与版本：[批次 ID、提交或文件哈希清单]
已实现：[本批明确范围]
接口与接入：[最小接线说明及兼容前提]
证据：[测试/截图/日志位置；本次执行或复用的依据]
未通过及未验证：[失败、待实机/线上等，明确归属]
共享变更需求：[无 / 必需事项与建议修改者]
资源状态：[仍在运行的本方进程、占用和需要保留的数据]
请求：[确认接收或具体返修；准备下一批分工]
```

接收者明确回复“本批接收”或具体返修项，说明这次接收覆盖的范围。只有测试通过但未做约定审查时，不冒称接收；已审查满足范围时及时给结论，不为了等待一个措辞而额外循环验收。不得因交付清单更新就使所有未变证据失效。

## Goal 轮转约定

以下是给用户审阅的授权文案，不是技能自动给予的授权：

> 用户授权协调对话 [ID/主机] 与执行对话 [ID/主机] 就本项目批次任务直接互发分工、接口、交付和接收消息。执行对话仅在当前 Goal 实际完成且下一批已明确分配后，为下一批创建 Goal，无须逐次询问。每批完整保留用户确认的固定协作规则，仅更新批次内容，并在创建后独立读回核验。授权仅限 [项目与任务范围]；用户后续暂停、清除、停止及预算限制优先。

### 固定规则与当前批次

把用户确认的目标分成两个部分，沿用已有任务记录保留可核对的完整文本：

- **固定规则**：协作身份及授权范围、项目边界、文件归属原则、原有功能／视觉标准、测试与输入隔离、交付接收条件、用户控制以及 Goal 接续约定。下一批完整复制，不重新概括，不用“沿用之前要求”替代正文。用户新指令优先；正式分工可以细化批次，不能默默删除固定约束。
- **当前批次**：具体模块、允许修改的文件、共享接口、依赖、验证与证据、接收者和完成条件。只更新这部分，保留本批返修及后续验收的归属。

不要把项目固定规则写死进通用技能。模板中的占位符须替换成该项目实际核实的内容；跨项目使用时不能继承旧身份、路径或授权。

派工者在发送候选 Goal 前、执行者在创建前，检查宿主实际长度及工具能力限制。对最终完整正文计数，包含标题、固定规则和当前批次；按宿主实际计数方式核对，不把某次观察到的上限当作所有客户端的常量。不靠反复提交超长正文来试探。

超过上限时，保持固定规则原文，先去掉当前批次的重复背景和重复嵌入数据；明确范围、文件归属、接口、验收及完成条件仍须保留，不能借精简改变任务。允许外部承载的详细规格可按可读位置和版本引用，创建前实际读取并核对。用户要求本批说明也逐字完整保留时，不能擅自精简。

仍放不下时保留完整文本并说明限制。仅在用户已明确接受引用式承载时，可将固定规则置于项目内稳定、可访问且有明确版本的文档，Goal 写清路径与版本并保留本批结果、边界和完成条件；每次接续／恢复都实际读取并核对该文档，无法读取或版本变化未经确认时不假定约束已继承。用户要求固定规则全文保留时，不擅自切换为引用式方案。

### 接续与独立读回

当前工具支持时，按以下顺序执行：

1. 读取当前对话的实际 Goal，并核对用户最新指令、当前批次和授权；不把另一对话或旧消息的状态当作本对话状态。
2. 本批满足既定完成条件并获约定接收后，才标记完成并核对结果。若完成操作结果不明确，先读取状态，不重复发送变更。
3. 有正式下一批分工且创建授权仍有效时，核对派工回执及正文长度，以“完整固定规则＋新批次”调用创建工具。主线程可以提前准备分工，但不能因此提前完成旧 Goal。
4. 创建后立即调用独立读取工具（如当前环境提供的 `get_goal`），核对完整目标正文、批次和实际状态。只忽略不改变文本含义的换行编码差异；规则遗漏、正文截断、批次或状态不符都不算验证通过。
5. 在已有任务记录中记下批次、固定规则版本或完整文本、接收证据、创建结果与读回结果。恢复上下文及批次交接时再核对，避免高频无变化轮询。

只有本次创建后的独立读回匹配，才能报告“新 Goal 已建立并核验”。创建返回成功、对话持续运行、UI 显示及任务已开工是不同证据，不能互相替代。工具不可用或只返回截断正文时，明确记录未核验，不宣称保存成功。

### 缺失或不一致时的有限恢复

先停止重复创建，核对查询是否成功、对话身份、最新用户指令、生命周期及并发更新。可做一次只读复查；空值本身不证明 Goal 丢失，也不构成恢复授权。

- **已有目标或正文／状态不一致**：保留现状，检查是否是用户编辑或另一个执行者的更新。不得覆盖、清空或把未完成目标标为完成来修复不一致。
- **用户暂停、清除、停止或达到预算限制**：尊重该状态，不自动恢复，也不通过创建新 Goal 重置或绕过限制。
- **确认创建未保留、目标仍应存在**：仅当当前仍无未完成 Goal、原创建授权有效，并且能排除用户清除／暂停、预算限制及并发替换时，使用原完整正文最多补建一次，随后再次独立读回。无法排除时不猜测补建。
- **原因不明或补建后仍异常**：保存相关结果并报告，停止自动补建，不循环重建或伪造“已恢复”。依据现有工具的实际规则处理状态，不为了退出而虚报完成或阻塞。

以上是流程防护，不是持久化修复或后台恢复服务。技能不存储 Goal；创建后读回成功也不保证未来永不异常。官方背景见 [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)：Goal 属于对话状态，用户和系统控制其生命周期。

若当前工具只能修改状态，不能修改正文，不要求执行者“自行改写未完成 Goal”。可在原目标范围内更新批次计划；超出原范围或必须替换目标时，说明需要用户编辑或使用已授权、正式支持的接口。不直接改 Codex 数据库或会话文件，不伪造消息。也不要把普通跨对话消息当成用户的 Goal 编辑操作。

### Goal 模板

以下仅表示结构；必须填入完整固定规则，不能把方括号提示或这个结构本身当作已经继承约束的 Goal：

```text
完成 [批次 ID/模块]，交付 [具体行为及产物]。

固定协作规则（每批完整保留）：
[粘贴用户已确认的完整固定规则，含身份、授权、范围、归属、
测试与隔离、验收、用户控制、接续及读回核验要求；不自行摘要。]

当前批次（仅本部分及开头的批次名称随正式分工更新）：
协调者与接收者为 [ID/主机]。
允许修改 [具体文件]；共享归属、接口和依赖为 [本批实际约定]。
必要验证及证据为 [检查条件与输出位置]。
完成条件为 [实现、必要验证、交付资料和接收条件]。
后续验收与返修归属为 [明确责任，不冒称已通过]。
```

只有本批 Goal 完成，不等于整个项目完成。尚未分配的任务不是虚构的“下一批”。无下一批时结束本批并等待；如果用户要求未来主动跟进，另按环境支持的调度工具处理，不以技能文案冒充后台服务。

## 审查调度是否有效

有现成记录时比较：交付到接收的等待、待整合批次数、返修次数、共享资源等待，以及主线程是否仍在推进关键路径。不要为这些指标先造监控平台。

接力问题还需区分上一批收口、下一批正式派发和实际开工的时间；源码只读准备不等于已开始实现。修复一次派工阻塞不证明长期稳定，可在后续实际批次中观察是否无需额外旁支介入；不为验证流程制造虚假批次、额外目标或后台轮询。

- 空闲发生在主线程整合期间：先检查能否准备独立下一批，而非立即增加名额。
- 有就绪任务却仍等待：核对派工是否落入账本并送达、旧预留状态是否被明确承接，优先补齐这一次交接。
- 多个批次都待接收：优先整合，限制新派工。
- 文件冲突持续发生：缩小修改范围或把共享接口收回单一负责人。
- 无新证据却频繁发消息：改为一次交付加有变化才通知。
- 主线程暂不可用：保存交付，不越权自我接收或伪造反馈。
