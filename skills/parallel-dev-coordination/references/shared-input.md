# 共享输入与测试隔离

仅在任务涉及图形界面、真实设备或共享运行环境时读取。不是每个并行开发项目都需要桌面锁。

## 区分系统输入与进程内测试

同一桌面的鼠标、键盘和前台焦点是共享资源。隐藏窗口中的指针移动（例如 Godot 的 `Input.warp_mouse()`）、切换前台、启动时激活窗口，也会产生影响；仅注入进程内事件的测试仍须检查是否间接调用这些操作。

截图应绑定目标进程/视口或已确认的窗口。全桌面截图和依赖前台焦点的定位也需要协调。无界面断言不能证明视觉渲染；离屏渲染必须确认实际输出与隔离能力，不能仅凭一个启动参数认定。

不同端口不代表不同账号、存档或数据库；不同工作树不代表不同构建缓存、输出、设备或服务。按实际副作用隔离，不为形式上的隔离复制完整环境。

## 优先复用现有入口

读取项目已验证的输入锁/测试入口及使用约定。模块执行者让专属 runner 复用该入口，协调者维护共享实现；每批不另造锁。

必须修改共享入口时，由明确负责人做小范围接入，不能让所有开发等待一项庞大调度工程。暂时没有机制时，按一批测试一次性约定输入时段，期间其他执行者继续静态工作；不为每次点击或重跑索取批准。

自动互斥的适用条件：

- 获取须原子化，覆盖同一资源的全部相关对话和子进程；只做“先看没有进程，再启动”存在竞争窗口。
- 一批入口持一次锁；明确包装层与原生持锁 runner，避免父进程持锁后又等子进程取得同一锁。
- 释放前等待本方输入子进程结束，错误/超时路径也处理本方后代。不能终止无关或归属不明的进程。
- 失效锁回收核对拥有者、进程身份及关联子进程；时间到期或 PID 不存在单独不能证明资源已安全释放。
- 拿不到锁时有界排队或记录待测，继续其他工作；不能无锁降级运行。
- 机器记录批次、拥有者、取得/释放、进程及错误；正常取得/释放不变成人工消息往返。

## 决策示例

| 实际情况 | 安排 |
| --- | --- |
| 两个独立纯逻辑测试，无共享可写状态 | 可以并行，不申请桌面锁 |
| 两个 GUI 测试均会移动系统鼠标 | 输入阶段串行，其他开发照常 |
| 只渲染专属视口、无系统输入且不会激活窗口 | 确认隔离和硬件余量后可并行 |
| 同一个设备或相同测试账号 | 明确唯一控制者，或使用真正隔离的测试对象 |
| 主线程正在静态接线 | 不因其“忙碌”阻止持锁测试 |
| 锁异常，无法确认原输入进程是否停止 | 不启动新的冲突输入，交由资源负责人处理 |

验证互斥时检查真实重叠、排队、异常退出和回收行为；离线 mock 通过不能声称真实桌面已验证。输入锁通过也不等于模块、实机或阶段验收通过。
