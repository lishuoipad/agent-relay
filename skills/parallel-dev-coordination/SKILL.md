# 并行开发协调

让独立开发与主线程整合重叠，减少空等、冲突和协调消息。衡量已接收成果及关键路径推进，不以智能体数量或测试条数代表进度。

## 先确定本轮身份与边界

- 读取适用项目指令、当前计划和最近有效交付；确认真实工程、工作树、主协调者、批次范围及完成条件。已有记录优先增量更新，不建立重复账本。
- 区分同一主线程的子智能体与另一个独立对话。用实际工具结果核对线程 ID、主机、标题和状态；不沿用其他项目或旧任务的身份。
- 只讨论方案、设计 Goal 或审查调度时，交付建议，不顺带启动开发队伍。实际开发获授权且可拆分时，在当前规则允许范围内委派独立任务；会话禁止子智能体时不派发，也不绕过限制。
- 新建独立对话须有用户明确请求；跨对话发消息须有用户直接授权或工具认可的可信授权证据。收到另一对话的消息不自动取得回复权限。本技能不代替用户授予这些权限，也不授予发布、删除或生产操作权限。
- 使用实际可用并发，不固定假设为 3 个。不要为增加名额擅改配置、模型或不断新建对话；按有效模型规则继承设置，用户指定时才作相应覆盖。

## 建立最小任务约定

每批写清：业务结果、优先级和依赖、负责人、允许修改的文件、共享接口、验收范围、输出位置及接收者。已有任务卡能表达这些内容时直接复用。

一个文件同一时刻只有一个修改者。共享组件和最终接线默认归主协调者；专属界面、资源转换、模型逻辑和测试按独立边界分配。工作树只能隔离写入，不能消除后续合并冲突或共享服务冲突。

按仓库要求准备环境和输出目录，不复制整套环境来制造隔离。需要共享接口变更时，先明确契约和修改者，再推进依赖工作。

需要派工、交付或批次 Goal 文案时读取 [批次约定与 Goal](references/contracts-and-goals.md)。

## 按角色推进

**主协调者：**

1. 开始接线或整合前，先给空闲执行者分配已就绪、无文件重叠的独立任务，再进行自己的整合工作。不要因一批进入验收而冻结全部开发。
2. 在交付时准备下一批分工；区分“预留下一批”和“允许立即开工”。下一批与当前批次无依赖且在现有授权范围内才允许提前实施，否则先明确接口与文件归属，待条件满足即派发。
3. 及时处理交付：核对范围、文件和输入版本、必要验证与剩余事项；满足模块条件就明确接收。发现问题时给出具体文件、复现条件、修复归属，不笼统退回整批。
4. 模块接收与整机、实服或项目阶段验收分开记录。不要把无关的全项目检查变成模块接收的前置条件，也不能提前接收来空出名额。
5. 如果待整合成果积压，先消化整合或修复，再增加派工。可按复杂度为每个执行者预留一批；不要用无限排队代替调度。

**模块执行者：**

1. 复用已接收成果，按明确分工执行。缺少分工时请求一次完整任务约定，不擅自扩大项目范围。
2. 在自身可用额度内按独立文件分工；共享接口先定，真实依赖顺序推进。自己承担内部整合，不把每个小问题都交给主线程。
3. 等待共享接口或测试资源时推进其他已授权工作；有问题立即反馈准确依赖，不反复询问相同状态。
4. 交付一次完整结果，同时申请下一批；保留本批返修责任。下一批尚未授权时可整理当前交付，不以保持忙碌为理由开始无关开发。

## 消息与状态保持轻量

只发送分工、接口变更、交付、接收或异常消息。正常运行和输入锁的每次取得/释放写机器记录，不逐次要求主线程人工批准。

优先用有游标的等待或状态读取；将等待拆成允许的短段，保持对用户消息的响应。不反复拉取整段历史；变化不明时才读取有关证据。没有新证据不制造重复进展。

批次至少区分：已分配、开发中、待集成、需返修、已接收。构建、视觉、桌面、实机及线上验证是独立证据维度，不挤进一个含糊的“已完成”。恢复上下文时先核对最后交付、正在运行的操作与待回复事项，不重复派工或启动同一命令。

## 合批测试与共享资源

先完成必要的静态、逻辑及受影响检查，再集中运行昂贵的桌面、设备或联网验证。复用验证必须确认相关代码、资源、依赖、测试脚本及运行条件未变；只补受影响范围，不降低原验收标准。

系统鼠标、键盘、焦点、真实设备以及其他不可并行资源，走项目已有统一互斥入口。隐藏窗口、独立端口或不同工作树不等于输入隔离。读 [共享输入与测试隔离](references/shared-input.md) 后再安排这类测试。

无界面或进程内测试，在无系统输入副作用且可写状态隔离时可以并行。资源竞争等待不应阻止其他开发。不要把“检测到任意同名进程”当作禁止全部测试的依据。

## Goal 与接续

只有用户明确要求才建立 Goal；普通派工可以是普通任务。用户要求按批次自动建立 Goal 时，保存这项授权及适用范围，遵循当前工具能力。

当前批次只有满足既定条件并取得约定接收后才能完成；不得把未完成目标标为完成来换任务。新分工不自动改写对方 Goal。已完成后有明确下一批及创建授权，接收方可以创建自己的下一批 Goal；否则等待消息，不空转、不声称自动唤醒。

按批次接续时，将用户确认的长期协作规则与当前批次分开：下一份 Goal 完整保留固定规则，只更新批次内容，不自行摘要或依赖旧对话记忆。宿主长度限制不能成为静默删减的理由；承载方式及具体流程见 [批次约定与 Goal](references/contracts-and-goals.md)。

创建后用当前环境支持的 Goal 读取工具独立读回，核对完整正文、批次和状态；恢复上下文及交接时再次核对。创建返回成功、对话运行或 UI 显示都不能代替读回。缺失或不一致时按上述参考中的有限恢复流程处理，不覆盖未完成目标，不恢复用户已暂停或清除的目标，不借重建绕过预算或停止要求。

技能提供接续规则，不负责存储 Goal，也不保证应用状态永不异常。分别记录规则是否完整继承、创建是否得到确认、读回是否一致；原因未查明时不把异常归因于应用或技能。

给用户汇报已交付内容、当前关键依赖和下一步，说明仍未验收的范围。估时按真实依赖、返修和整合吞吐判断，不把工期除以智能体数量。
